## Хранение данных и миграции схемы

Все данные проекта живут в localStorage браузера (ключ `draftkeeper_data_v1`),
backend/базы данных нет. Это значит: при любом изменении формы объектов
(project/chapter/character/note/branch/timeline) уже существующие локальные
данные пользователя должны автоматически привестись к новой форме сами —
никакого отдельного скрипта миграции "на сервере" не будет, всё происходит
в браузере пользователя при следующем открытии.

**Правило: любое изменение структуры данных обязано сопровождаться
миграцией.** Нельзя полагаться на то, что новое поле "просто появится" у
всех — старые локальные данные останутся без него, и код упадёт при первом
же обращении к несуществующему свойству.

### Где писать миграции

В `src/app.js` есть функции-мигранты для каждого типа сущности:
- `migrateCharacter(c)` — персонаж
- `migrateNote(n)` — заметка
- `migrateChapter(ch)` — глава
- `migrateProject(p)` — вызывает три предыдущие плюс поля самого проекта
  (например `p.notes`, `p.driveBackup`)

Вызываются в двух местах — оба должны остаться покрыты при любом изменении:
1. `loadAll()` — при каждом обычном открытии приложения
2. обработчик `importFile` (импорт JSON) — при загрузке чужого/старого файла

Если добавляешь новое поле — допиши в соответствующую `migrateX`:
`if (!x.newField) x.newField = <значение по умолчанию>;` (для объектов/
массивов — аналогичная проверка на существование). Если переименовываешь
или меняешь форму существующего поля — перенеси значение из старого имени в
новое и удали старое. Пример уже есть в `migrateCharacter`:
`character.desc` → `character.appearance.description`.

### Требования к миграциям

- **Идемпотентность**: миграция должна быть безопасной при повторном запуске
  на уже мигрированных данных — проверять `if (!x)` перед тем как выставлять
  значение по умолчанию, никогда не выставлять безусловно.
- **Не терять данные пользователя**: если старое поле содержало текст/
  значение, оно должно переехать в новое поле, а не быть просто отброшено.
- **Не крашиться на недостающей вложенности**: сначала гарантировать сам
  объект-контейнер (`if (!c.appearance) c.appearance = {...}`), потом уже
  обращаться к его полям.

### Резервная копия перед миграцией

`loadAll()` перед миграцией сравнивает JSON-снимок данных до и после; если
миграция что-то изменила, кладёт немигрированный снимок в localStorage под
ключом `draftkeeper_data_v1_backup_before_migration` и сразу сохраняет
мигрированную версию как основную. Ничего в этом механизме менять не нужно
при добавлении новых миграций — он автоматически ловит любое изменение,
которое проходит через `migrateProject`.

### Проверка после любой миграции — обязательна

1. Собрать объект в "старом" формате (до изменения) напрямую через
   localStorage/консоль браузера
2. Перезагрузить страницу, убедиться что интерфейс не падает и данные видны
3. Проверить, что старые данные не потерялись, а корректно переехали в
   новую форму (сравнить конкретные значения, не просто "не упало")
4. Прогнать полный цикл экспорт → импорт на мигрированных данных

## Деплой

Сайт публикуется на GitHub Pages автоматически через GitHub Actions при
каждом `git push` в `main` (см. `.github/workflows/deploy-pages.yml`,
деплоит содержимое `src/`). Ручных действий на хостинге не требуется.

При любом изменении файлов внутри `src/` — поднимать `CACHE_VERSION` в
`src/sw.js`, иначе у пользователей с уже закэшированной версией (service
worker) новые файлы не подтянутся. Пользователи увидят баннер "Доступна
новая версия" автоматически — специально ничего им сообщать не нужно.
